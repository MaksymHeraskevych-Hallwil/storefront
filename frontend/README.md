# frontend

Next.js 16 (App Router) + shadcn/ui. Адмін-панель StoreFront.

## Чому shadcn/ui, а не Polaris

Бриф просив Polaris, але `@shopify/polaris` (React-пакет) виявився
офіційно deprecated — Shopify більше його не підтримує, лише архівна
документація. Заміна ("Polaris web components") розрахована на
застосунки, вбудовані в саму адмінку Shopify (App Home/App Bridge),
а не на окремий самостійний сервіс на кшталт нашого — тож не підходить
за задумом. Замість цього — shadcn/ui: не npm-залежність, а джерельний
код компонентів у самому репозиторії (`src/components/ui/`), нічого
не "зникне" з-під ніг.

**Реальна несподіванка:** поточний стиль shadcn ("base-nova") збирає
компоненти на [Base UI](https://base-ui.com/), не на Radix. Композиція
інша: замість `<Button asChild><Link .../></Button>` тут
`<Button render={<Link ... />} nativeButton={false} />`.

## Стек і конвенції

- **Next.js 16.3.5**, App Router, TypeScript, Turbopack (дефолт для `next dev`).
- **React 18**, не 19 — `@shopify/polaris` уже прибрано, але React лишили
  на 18, бо саме на ньому усе перевірено; піднімати versiю окремо не було приводу.
- **Tailwind CSS v4** (CSS-first конфіг, без `tailwind.config.js`) + shadcn/ui.
- **Zustand** — під'єднано, ще не використовується: перших клієнтських
  UI-станів (bulk-select, чернетка форми) поки що не з'явилось.
- `proxy.ts` (у 16-й версії Middleware перейменували на Proxy) —
  оптимістична перевірка сесії за наявністю куки `token`, без звернень
  до бекенду. Справжню валідність токена перевіряє сам бекенд;
  прострочений/підроблений токен ловить `(admin)/layout.tsx` (401 → редірект).

## Як дані доходять до сторінок

Два різні шляхи, і обидва навмисні:

- **Браузер → nginx → backend.** Клієнтський код (форма логіну,
  logout) б'є у відносний `/api/...` — той самий origin, кука
  прикладається сама, CORS ні до чого.
- **Сервер (Server Components) → backend напряму.** `src/lib/api.ts`
  ходить у `BACKEND_INTERNAL_URL` (`http://backend:5051`), в обхід
  nginx — швидше, і це вже інший процес, тож кука форвардиться вручну
  (`cookies().toString()` у заголовок `Cookie`).

## Локальний запуск

Той самий підхід, що й у backend — контейнер, hot-reload через volume,
нічого не запускається напряму на хості:

```bash
cd ..                      # корінь storefront/
docker compose up -d --build
```

Усе через **http://localhost** (nginx, порт 80) — не `:3000`, він не
опублікований.

## Ендпоінти адмінки

| Шлях                 | Опис                                          |
| --------------------- | ---------------------------------------------- |
| `/login`              | Форма входу                                    |
| `/products`           | Список товарів — пагінація, пошук, фільтр статусу |
| `/products/new`       | Створення товару                               |
| `/products/:id`       | Картка товару — редагування, варіанти, кастомні поля |
| `/orders`             | Список замовлень — фільтр статусу, пагінація   |
| `/orders/:id`         | Замовлення — позиції, зміна статусу лише дозволеними кнопками |
| `/support`            | Список тікетів підтримки — фільтр статусу, пагінація |
| `/support/:id`        | Тікет — листування, форма відповіді (з опцією "закрити"), ручна зміна статусу |
| `/analytics`          | Дашборд — виручка, замовлення, нові клієнти (картки + графіки по днях), топ-5 товарів; фільтр періоду (7/30/90 днів, весь час) |

Кнопки зміни статусу замовлення — не довільний select, а лише ті
переходи, які віддає `allowedTransitions` з `GET /api/orders/:id`.
Стейт-машину (яка кнопка коли з'являється) фронт не дублює — це
відповідальність бекенду.

Статус тікета, навпаки, — звичайний `<select>` без обмежень: бекенд
свідомо не має таблиці дозволених переходів для підтримки (див.
`../backend/README.md`), тож і фронту нема що звіряти. Відповідь
персоналу (`ReplyForm`) сама рухає статус на бекенді — чекбокс
"закрити тікет цією відповіддю" просто передає `close: true` в тілі
запиту.

Фільтр періоду на `/analytics` — звичайні посилання (`?days=7` тощо),
не клієнтський стейт: та сама логіка Server Component + `searchParams`,
що й у фільтра статусу на `/orders` і `/support`.

Графіки — свій невеликий `src/components/bar-chart.tsx` без чарт-бібліотеки
(стовпчики — звичайні `<div>`, ≤24px, закруглений верх; hover-підказка
з точним значенням; `<details>` з таблицею тих самих даних для
доступності). Топ-товари — прогрес-бари тим самим підходом.

**Дві реальні пастки, спіймані в браузері:**

- Server Component не може передати в клієнтський компонент функцію
  (`format={(v) => ...}`) — "Functions cannot be passed directly to
  Client Components". Тепер сторінка передає серіалізований
  `kind="currency" | "count"`, а форматує сам графік.
- Помилка гідратації: `Intl.NumberFormat("uk-UA", { currency: "UAH" })`
  у Node-контейнері дає "грн", а в браузері "₴" (і "1 тис." проти
  "1,0 тис." у compact-режимі) — сервер і клієнт видавали різний
  текст. У клієнтському компоненті форматування зроблено вручну
  (`formatNumber`), без `Intl`.

Мутації — через [Server Actions](node_modules/next/dist/docs/01-app/01-getting-started/07-mutating-data.md)
(`products/actions.ts`), не через client-side `fetch`: форма шле
`FormData` прямо на сервер, `revalidatePath` оновлює кеш роута.

**Реальна пастка, знайдена руками, не в довідниках:** `nginx` за
дизайном не успадковує `proxy_set_header` з рівня `server`, щойно
`location` додає СВІЙ хоч один такий заголовок (у нас — `Upgrade`
для HMR). Через це `location /` втратила `Host`, Next.js бачив
`Host: frontend:3000` замість `localhost`, і Server Actions падали
з "Invalid Server Actions request" (CSRF-перевірка Origin ≠ Host).
Виправлено в `../nginx/nginx.conf` — усі чотири заголовки продубльовано
явно в `location /`.

**Друга пастка:** форма редагування товару використовує
`defaultValue` (неконтрольовані поля) — React не оновлює їх при
ре-рендері з новими props, тільки при монтуванні. Після успішного
збереження статус/постачальник продовжували показувати старі
значення, хоча в базі вже лежали нові (перевірено напряму через API).
Фікс — `key={product.updatedAt}` на `<ProductEditForm>`: змінюється
`updatedAt` → форма ремаунтиться → `defaultValue` підхоплює свіжі дані.
Той самий трюк повторили в `support/[id]/reply-form.tsx`
(`key={ticket.messages.length}`), щоб textarea відповіді очищалась
після успішної відправки, а не лишала стару чернетку.
